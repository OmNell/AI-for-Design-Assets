   ## 3. 身份与 NAS 访问

   ### 3.1 登录

   1. 前端提交 NAS 用户名、密码到 `POST /api/auth/login`。
   2. 后端调 DSM 登录接口（`SYNO.API.Auth`）验证。失败 → 401，错误次数由 DSM 自己管。
   3. 成功 → 后端用同一组凭据建立该用户的 **SMB 会话**（`smbprotocol` 库，程序内连接，不挂盘），放进会话池。
   4. 查角色表得到角色；签发工作台会话令牌（随机 256 位，存 SQLite `sessions` 表），通过 HttpOnly Cookie 下发，8 小时。
   5. 密码在第 3 步用完即丢，不落盘、不进日志。DSM 的登录令牌也只存内存。

   ### 3.2 NAS 会话池

   ```
   SessionPool
     get(user_id) -> SmbSession        # 没有则抛 NotLoggedIn
     open(user_id, username, password) # 登录时调用
     close(user_id)                    # 退出 / 超时
     system()                          # 系统账号的会话（巡检只读 + 备份写）
   ```

   - 每个在线用户一条 SMB 连接，自动重连；空闲 30 分钟关闭，下次请求时用会话里缓存的 DSM 令牌重开（**【待定】重开 SMB 需要密码，DSM 令牌换不来 SMB 凭据，两种处理：要么会话内存保留密码直到退出，要么空闲后让用户重新登录。建议后者，简单且安全**）。
   - 所有 NAS 路径操作统一走 `NasFs` 接口，上层代码不直接碰 SMB：

   ```
   NasFs(session)
     list(path) · stat(path) · open_read(path) · open_write(path, append=False)
     mkdir(path) · rename(src, dst) · delete(path) · exists(path)
   ```

   - 移动 = 同卷 `rename`，瞬时完成。临时区与正式目录必须在同一共享文件夹（同卷），否则 `rename` 退化为复制。

   ### 3.3 NAS 账号规划

   | 账号                     | 临时区 | 正式目录 | 备份目录 | 用途             |
   | ------------------------ | ------ | -------- | -------- | ---------------- |
   | 普通员工（上传人、初审） | 读写   | 只读     | 无       | 上传、下载       |
   | 终审                     | 读写   | 读写     | 无       | 入库、入库后操作 |
   | `wb-system`（系统账号）  | 无     | 只读     | 读写     | 巡检、备份       |

   系统账号的密码加密存在工作台配置里（见 12.2），是**唯一**落盘的 NAS 凭据。

   ### 3.4 权限执行点

   工作台只做两层控制：

   1. **角色检查**：接口按角色放行（上传人 / 初审 / 终审 / 管理员）。
   2. **NAS 权限**：所有文件操作用本人会话执行，NAS 拒绝就返回 403，前端原样提示"NAS 无权限"。

   不在工作台里复制一份 NAS 的目录权限。

   ## 4. 技术栈与关键库

   ### 4.1 后端

   | 用途     | 选型                                  | 说明                                      |
   | -------- | ------------------------------------- | ----------------------------------------- |
   | Web 框架 | FastAPI + Uvicorn                     | 同时托管 `/api/*` 和前端静态文件          |
   | ORM      | SQLAlchemy 2.x + Alembic              | 迁移脚本随代码走                          |
   | 数据库   | SQLite，WAL 模式，`busy_timeout=5000` | 单文件 `data/app.db`                      |
   | 向量     | sqlite-vec 扩展                       | 向量存在同一个库里，余弦相似度查询        |
   | NAS      | smbprotocol                           | 纯 Python SMB2/3 客户端，支持按连接传凭据 |
   | DSM API  | httpx                                 | 只用登录接口                              |
   | AI       | httpx + 百炼 OpenAI 兼容接口          | 不绑 SDK，方便换模型                      |
   | 图片     | Pillow（+ pillow-heif 预留）          | 缩略图、去 EXIF                           |
   | 指纹     | hashlib SHA-256                       | 流式计算                                  |
   | 定时     | APScheduler                           | 巡检、备份                                |
   | 配置     | pydantic-settings                     | `config.yaml` + 环境变量                  |
   | 加密     | cryptography（Fernet）                | API Key、系统账号密码                     |
   | 日志     | 标准 logging → 按天滚动文件           | 应用日志，与业务操作日志分开              |

   ### 4.2 前端

   | 用途       | 选型                                                         |
   | ---------- | ------------------------------------------------------------ |
   | 框架       | React 18 + TypeScript + Vite                                 |
   | 样式       | Tailwind CSS + liquid-glass-react                            |
   | 路由       | react-router                                                 |
   | 服务端状态 | TanStack Query                                               |
   | 本地状态   | zustand（视觉模式开关、上传队列）                            |
   | 表单       | react-hook-form                                              |
   | 上传       | 自研分片上传器（File System Access API / webkitdirectory 读目录，fetch 分片） |
   | 图片查看   | 自研（缩放、并排）                                           |

   **视觉模式**：全局 `GlassProvider`，两档：`full`（所有玻璃组件启用实时滤镜）/ `lite`（只有导航、卡片容器、弹窗、按钮用玻璃，列表项用 Tailwind 半透明样式）。存 localStorage，右上角一键切换。Safari/Firefox 自动降级为 `lite`。

   ## 8. 后台任务

   ### 8.1 队列

   - `jobs` 表即队列。工作线程池（默认 4 线程）轮询 `queued` 任务，抢占时用 `UPDATE … WHERE status='queued'` 保证不重复。
   - 每类任务有独立并发上限：AI 调用 3、缩略图 2、入库 1、巡检 1、备份 1。
   - 失败重试：AI 类 3 次，其余 1 次；超过则 `failed` 并进管理员异常列表。
   - **需要用户 NAS 身份的任务**（入库、入库后操作、档案修复）记录 `run_as_user_id`，执行时从会话池取该用户的会话；取不到（用户已退出、服务重启）→ 任务标 `failed`，批次标「入库异常」，等终审下次登录点「继续」。
   - 服务重启时：`running` 状态的任务重置为 `queued`（AI、缩略图）或 `failed`（入库，等待人工继续）。

   ### 8.2 任务类型

   | 任务             | 触发                             | 做什么                                                       |
   | ---------------- | -------------------------------- | ------------------------------------------------------------ |
   | `thumb`          | 主图分片完成                     | 生成 300 / 1600 / 1024 三档到 `data/thumbs/{batch 或 product}/` |
   | `ai_tag_batch`   | 上传人确认                       | 编排：位置查表 → 逐单品 `ai_tag_product` → 逐套装打标+关系推荐 → 状态改「待核对」 |
   | `ai_tag_product` | 上一项派生 / 单张重试 / 追加主图 | 调识图模型，按字段填写说明自由填写，拆分 terms，写 `batch_products.tags` |
   | `embed`          | 入库完成 / 改标签 / 改描述       | 用「标签拼接 + 自由描述」算向量写 `product_embeddings`       |
   | `ingest`         | 终审通过                         | 第 9 节的 9 步                                               |
   | `postop`         | 终审通过入库后操作               | 按 kind 分派                                                 |
   | `inspection`     | 每天 02:00                       | 第 14.2 节                                                   |
   | `backup`         | 每天 03:00                       | 第 13 节                                                     |

   ## 9. 入库执行器（幂等设计）

   每步执行前检查"是否已完成"，完成则跳过，所以从任意步重跑都安全。

   | 步   | 动作                                    | 幂等检查                                             |
   | ---- | --------------------------------------- | ---------------------------------------------------- |
   | 1    | 目标路径不存在同名/同编号文件夹         | 存在且 `projects.current_path` 已指向它 → 视为已完成 |
   | 2    | 按对照表建行业、企业文件夹              | `exists`                                             |
   | 3    | `rename(临时区/批次/项目文件夹 → 目标)` | 源不存在且目标存在                                   |
   | 4    | 发商品编号                              | `batch_products` 已有 `product_code`                 |
   | 5    | 写 SKU 档案                             | 文件存在且结束标记为「完」                           |
   | 6    | 建 `_历史版本/`，写项目档案             | 同上                                                 |
   | 7    | 写卡片柜（事务）                        | `projects.status='active'`                           |
   | 8    | 生成链接                                | `links` 已有                                         |
   | 9    | 批次「已入库」，待办通知，派发 `embed`  | 状态                                                 |

   `batches.ingest_step` 记录最后完成的步骤号。

   ## 10. 检索引擎

   ```
   用户输入
     │
     ├─ 像编号（立项编号、商品编号的格式）→ 精确查 → 置顶
     │
     └─ 自然语言
          ├─ 缓存命中（query 文本哈希）→ 取已翻译条件
          └─ 调文本模型理解查询 → {各字段的关键词及其同义说法, 排除词, 其他关键词}
               │   （例：「过年送领导」→ 节日场景:[春节,过年,新年]，受众群体:[领导,企业客户,上级]）
               │
               ├─ 路 A：字段关键词匹配（SQL：在对应字段的 terms 和自由描述里包含匹配，
               │        命中字段越多得分越高）→ 候选集 A
               ├─ 路 B：查询文本算向量 → sqlite-vec 取 Top-50 → 候选集 B
               └─ 合并去重（A ∪ B），最多 60 条
                    │
                    └─ 调文本模型排序（只发候选编号 1..N + 文字描述）→ Top-10
                         │
                         └─ 组装：主图缩略图、标签、所属套装、项目（企业/编号/中标）、链接
   同时：项目名 / 编号 / 企业名 LIKE 匹配 → 「项目命中」区块
   ```

   - 标签是自由文本，没有标准值可以精确比对，所以同义词扩展、向量和大模型排序共同承担「说法不一样」的问题。
   - 结果少于 10 时放宽：不再要求按字段匹配，改为所有关键词在全部字段和自由描述里任意包含 → 仍少则如实返回。
   - 已作废、已删除商品不进候选。
   - 每次搜索写 `search_logs`，供考卷补充。
   - 考卷：`tests/search_exam.yaml` 存 100～200 条查询及正确答案，一条命令跑出海选命中率、Top-3/Top-10 命中率、耗时、费用。

   ## 11. 关键流程（时序）

   ### 11.1 分片上传

   1. 前端读目录得到清单，本地预检，`POST /batches/precheck` 问编号。
   2. `POST /batches` 建批次，得到 `batch_id` + 上传令牌（独立于登录会话，有效期到批次完成）。
   3. 前端按「主图 → 小文件 → 大文件」排序，3 路并行，每文件 8MB 分片顺序 `PUT`。
   4. 服务端收到分片 → 用上传人 SMB 会话 `open_write(append)` 追加到 `临时区/{batch_no}/{rel_path}`，同时把分片喂给 SHA-256 增量器（状态存内存，重启后丢失则在 complete 时重新流式读一遍算）。
   5. `complete` 校验大小，写 `batch_files.fingerprint`；主图派发 `thumb`。
   6. 全部 done → 批次「已暂存」。

   ### 11.2 核对 → 入库

   前端只和 `batch_products` 打交道，直到终审通过，`ingest` 任务才把 `batch_products` 转成 `products`、`product_tags`、`product_relations`。

   ### 11.3 下载

   `GET /files/{id}/download` → 用当前用户 SMB 会话 `open_read` → `StreamingResponse`，支持 `Range`，NAS 拒绝即 403。

   ## 16. 部署（Windows）

   1. 安装 Python 3.12、Node 20（仅构建前端用；生产只需 Python）。
   2. `frontend`：`npm ci && npm run build` → 产物复制到 `backend/app/static/`。
   3. `backend`：创建 venv，`pip install -e .`，`alembic upgrade head`。
   4. 复制 `config.example.yaml` → `config.yaml`，填 NAS 地址、系统账号；启动一次生成 `secret.key`。
   5. 用 **NSSM** 把 `uvicorn app.main:app --host 0.0.0.0 --port 8080` 注册为 Windows 服务，自动启动、崩溃自动重启。
   6. 防火墙放行 8080；给这台机固定 IP；在内网 DNS 或各人 hosts 里加一个好记的名字（可选）。
   7. 浏览器访问 `http://<IP>:8080`，用管理员的 NAS 账号登录，在角色表里把自己设为管理员（首次启动时 `config.yaml` 里指定 `bootstrap_admin` 账号）。
   8. 设置页填百炼配置，点测试连接。
   9. 在 NAS 上（NAS 管理员手动做，一次性）：
      - 在**同一个共享文件夹**里建三个空文件夹：`设计资产/`（正式库空壳，里面的一切由工作台自动建）、`工作台临时区/`、`_工作台备份/`。
      - 建一个账号 `wb-system`，只给巡检和备份用：`设计资产/` 只读、`_工作台备份/` 读写、临时区不给。
      - 给普通员工：`设计资产/` 只读、`工作台临时区/` 读写；给终审：两者都读写。

   ## 18. 开发顺序与工作包

   工作包的划分和每个包的完整提示词见《Codex 分阶段提示词 v1》，本节只保留总览。

   | 阶段         | 工作包                                                       | 里程碑                                |
   | ------------ | ------------------------------------------------------------ | ------------------------------------- |
   | 0 探路与骨架 | WP00 探路 · WP01 骨架 · WP02 NAS 接入 · WP03 登录与界面框架  | ① 能用 NAS 账号登录，看到液态玻璃界面 |
   | 1 上传到核对 | WP04 分片上传 · WP05 任务队列与缩略图 · WP06 AI 打标 · WP07 核对页 | ② 拖入项目，AI 打完标，能在核对页修改 |
   | 2 审核到入库 | WP08 初审终审 · WP09 入库执行与档案 · WP10 项目页与下载      | ③ 完整走通入库，可上线试用            |
   | 3 检索       | WP11 检索引擎与搜索页                                        | ④ 能搜到商品并下载                    |
   | 4 运维与收尾 | WP12 入库后操作 · WP13 巡检备份与管理后台 · WP14 部署包      | ⑤ 正式上线                            |

   相对本文前面各节，提示词文档补充了三点实现约定：

   1. **三种运行模式**：`config.yaml` 增加 `mode: dev|prod`。dev 模式下登录用配置里的假账号、NAS 用本地文件夹模拟并按角色模拟权限、AI 用固定返回的假模型，全部自动化测试跑在 dev 模式；需要真实 NAS 或真实百炼的测试单独标记，由人在内网手动运行。
   2. **向量存储后备**：优先 sqlite-vec；扩展加载失败时自动退回「向量存 BLOB + 程序内计算余弦相似度」。
   3. **WP00 探路**：正式开发前先用独立脚本验证群晖的 DSM 登录、按账号建立 SMB 连接、权限生效和同卷移动。
