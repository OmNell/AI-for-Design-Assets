## 3. 身份与 NAS 访问

### 3.1 登录

1. 前端提交本人 NAS 用户名、密码到 `POST /api/auth/login`。
2. 生产后端用 `smbprotocol` 直接连接 NAS TCP 445，依次完成 SMB 协商、本人认证、会话校验和业务共享连接。应用要求会话签名，拒绝 Guest、匿名或 DFS 共享。每次登录绑定发起认证的 SMB 服务器。文件读取和写入继续按 NAS ACL 检查。
3. 后端核对本地账号启用状态与角色，将已认证的 SMB 连接绑定到本次工作台登录。签发随机 256 位令牌，以 HttpOnly Cookie 下发。SQLite `sessions` 保存令牌哈希，默认有效期 8 小时。
4. 网络、协议协商、认证、账号限制和共享权限错误按阶段提示。工作台账号的停用状态单独处理。普通用户密码仅在认证时短暂使用。

### 3.2 NAS 会话池

```text
SessionPool
  get(login_session_id) -> SmbSession  # 以工作台登录会话隔离，不以 user_id 唯一索引
  adopt(login_session_id, authenticated_fs) -> None
  close(login_session_id) -> None
  system() -> NasFs                  # 系统巡检和备份使用独立会话
```

- 同一 NAS 账号可在不同电脑同时登录，每次工作台登录对应独立的 Cookie、SMB 会话、超时和日志 `client_host`，不得使用 `get(user_id)` 导致跨设备串用连接。
- 普通用户密码只在登录／重新认证期间短暂使用，不持久化到数据库、配置或日志；已建立 SMB 连接可完成正在传输的数据。8 小时工作台会话届满后，禁止发起新的需认证操作；如果现有 SMB 文件写连接仍健康，允许当前文件传输到安全检查点后完成；连接掉线则保存偏移和分片状态，用户重新登录后恢复。
- 服务重启或本次 SMB 连接彻底断开后，用户须重新登录。上传令牌与批次和登录会话绑定。
- `NasFs` 统一封装 `list/stat/open_read/open_write/mkdir/rename/delete/exists`，所有路径映射、授权及日志均从服务层经过，移动可能需要跨目录复制＋校验＋删除，不能以 rename 必然原子作为业务前提。
- 正式目录修改由通过本轮终审的终审人 NAS 会话执行；其会话不可用时挂起为异常并保留可恢复进度。**不擅自增加其他终审人员接管功能**（问题 51 尚未确认）。

### 3.3 NAS 账号规划

| 账号 | 临时区 | 正式目录 | 备份目录 | 用途 |
|---|---|---|---|---|
| 普通员工（上传人、初审） | 读写 | 只读 | 无 | 上传、下载 |
| 终审 | 读写 | 读写 | 无 | 入库、入库后操作 |
| `wb-system`（系统账号） | 无 | 只读 | 读写 | 巡检、备份和恢复。恢复任务以只读连接访问正式区与备份区 |
| 管理员个人 NAS 账号 | 全临时区读、删除 | 无额外写权限（如另有终审角色则依该角色授权） | 无 | 清理终态批次临时文件 |

系统账号的密码加密存在工作台配置里（见 12.2），是**唯一**落盘的 NAS 凭据。

### 3.4 权限执行点

工作台只做两层控制：
1. **角色检查**：接口按角色放行（上传人 / 初审 / 终审 / 管理员）。
2. **NAS 权限**按当前操作所用的身份执行。业务文件使用本人会话，系统巡检、备份和恢复使用系统账号。NAS 拒绝业务文件操作时提示权限不足。

不在工作台里复制一份 NAS 的目录权限。

## 4. 技术栈与关键库

### 4.1 后端

| 用途 | 选型 | 说明 |
|---|---|---|
| Web 框架 | FastAPI + Uvicorn | 同时托管 `/api/*` 和前端静态文件 |
| ORM | SQLAlchemy 2.x + Alembic | 迁移脚本随代码走 |
| 数据库 | SQLite，WAL 模式，`busy_timeout=5000` | 单文件 `data/app.db` |
| 向量 | sqlite-vec，NumPy 后备 | 主库保存向量及代次信息。扩展不可用时由程序读取 BLOB 并在本地计算余弦相似度 |
| NAS | smbprotocol | Python SMB2/3 客户端，按会话传凭据并直连普通业务共享，拒绝 DFS 共享 |
| AI | httpx + 百炼 OpenAI 兼容接口 | 不绑 SDK，方便换模型 |
| 图片 | Pillow（+ pillow-heif 预留） | 缩略图、去 EXIF |
| 指纹 | hashlib SHA-256 | 流式计算 |
| 定时 | APScheduler | 巡检、备份 |
| 配置 | pydantic-settings | `config.yaml` + 环境变量 |
| 加密 | cryptography（Fernet） | API Key、系统账号密码 |
| 日志 | 标准 logging → 按天滚动文件 | 应用日志，与业务操作日志分开 |

### 4.2 前端

| 用途 | 选型 |
|---|---|
| 框架 | React 18 + TypeScript + Vite |
| 样式 | Tailwind CSS 与项目共享组件 |
| 路由 | react-router |
| 服务端状态 | TanStack Query |
| 本地状态 | zustand |
| 表单 | react-hook-form |
| 上传 | 自研分片上传器（File System Access API / webkitdirectory 读目录，fetch 分片） |
| 图片查看 | 自研（缩放、并排） |

首页、审核、资产浏览及管理页复用 `frontend/src/components/ui/` 的共享组件，并以桌面浏览器为主要使用环境。

## 8. 后台任务

### 8.1 队列

- `jobs` 表持久化任务、进度和结果。工作线程池默认 4 线程，按任务类型注册并发、重试和重启策略。
- 入库和入库后操作同时记录 `run_as_user_id` 与 `run_as_session_id`。原终审会话失效时保留检查点，等本人重新登录后继续。
- 服务重启后，运行中的 AI、批次缩略图、向量重建、巡检、备份与档案应用任务可重新入队。依赖原会话的入库和入库后操作由原终审继续。中断的检测、扫描、备份暂存和正式缩略图任务由管理员重新发起。
- 同一时刻只接受一项待执行或执行中的恢复任务。`asset_recovery_apply` 以独占方式运行，已进入执行的其他任务结束后再启动，执行期间暂停领取其他队列任务。

### 8.2 任务类型

| 任务 | 触发 | 做什么 |

## 9. 入库执行器（幂等设计）

原则：**每一步写持久化检查点，重跑只补未完成动作；完成全部必要商品向量后才能标记为「已入库」。** NAS 与 SQLite 不存在跨系统事务，必须先用批次数据制作可灾难恢复的档案，再投影到 SQLite。首次入库「入库中／入库异常」只对提交人、审核人、管理员展示。

| 步 | 动作 | 幂等检查／失败处理 |
|---|---|---|
| 1 | 检查项目编号及目标目录冲突 | 编号级进行中独占；已归属本批次的目录不是冲突 |
| 2 | 以终审 NAS 身份创建中标／行业／企业层级 | `exists` 检查，不覆盖已有目录 |
| 3 | 将项目文件夹从临时区移动到目标位置；按业务原名补齐五个空资料夹 | 校验来源／目标清单及 SHA-256；清理动作可恢复 |
| 4 | 先单品、后套装，发放商品编号写回 `batch_products.product_code` | 已发编号绝不重新发；历史 H 年份按提交人选择、独立流水并发唯一 |
| 5 | 依据已确认批次数据写 `单品档案/{product_code}.json` 和 `套装档案/{product_code}.json` | 原子写入、读回、结构化 `结束标记` 校验 |
| 6 | 创建 `_历史版本/`、写 `_项目档案.txt`，包括稳定 ID、永久 link_id／文件身份／历史关系 | 完全数据库丢失后能从档案恢复永久链接，内容足以重建 |
| 7 | 一个 SQLite 事务登记项目、文件、商品、关系、标签、历史和链接 | 状态仍为 `ingesting`；按固定 ID 幂等 UPSERT，SQLite 为之后变更权威源 |
| 8 | 核验／持久化所有项目／商品／文件链接和 NAS 档案映射，校验数据库档案一致 | `public_base_url` 统一内网域名；不能以 IP 拼接新链接 |
| 9 | 对每个商品计算必要文本向量、逐个核验模型／维度／文本哈希；全部成功才标 `active` 和「已入库」并通知 | 限次重试，失败状态 `ingest_error`／「入库异常」；保留已成功成果，终审重试缺失向量；旧索引双轨重建另见第 10 节 |

首次入库非商品文件无需向量；文档内容不全文向量化。第 5～6 步写档案必须具备灾难恢复的稳定商品／文件标识、link_id、完整 SHA-256、历史版本路径、标签确认值、套装关系和逻辑状态。`结束标记` 在 JSON 档案中是有效 JSON 字段（如 `"结束标记":"完"`），不得追加使 JSON 非法的尾行；TXT 项目档案使用文本结束行。

正式档案、文件身份和全部必要向量通过校验后，本轮终审会话写入并读回 `_历史版本/_发布凭据.json`，随后提交 SQLite 的正式可见状态。凭据记录项目 ID、编号、相对路径、资产版本和档案摘要。SQLite 完好且提交中断时，由本轮终审继续原批次。SQLite 和备份同失时，第 14.3 节的恢复流程可核验已落盘凭据。

## 10. 检索引擎

| 模式 | 查询链路 |
|---|---|
| 快速匹配（`quick`，界面默认） | 在本地识别项目或商品编号。按项目编号、名称、企业及当前检索字段中的词匹配，支持筛选与条件移除。返回匹配原因，全程零模型调用。 |
| AI 语义检索（`semantic`） | 完整编号直接查询。本地脱敏并缓存查询理解，模型提取字段关键词和同义说法。对符合关键词候选条件的商品查询正式向量，校验代次、维度和文本哈希，融合两路候选后交给文本模型排序。 |

- 查询理解、向量或排序失效时保留可用的本地结果，响应标记降级并展示原因。关键词可在严格匹配不足时放宽字段匹配；最终只返回实际命中。

- 搜索写入 `search_logs`，记录模式、耗时、使用的向量代次、降级及模型用量。预览和下载单独记录访问。评测和候选筛选细节见 [检索方案](04-检索方案.md)。

## 11. 关键流程（时序）

### 11.1 分片上传
1. 前端读目录得到清单，本地预检，`POST /batches/precheck` 问编号。
2. `POST /batches` 建批次，得到 `batch_id` 和绑定当前登录的上传令牌。续传重新核对文件清单与上传凭据。
3. 前端按「主图 → 小文件 → 大文件」排序，3 路并行，每文件 8MB 分片顺序 `PUT`。
4. 服务端收到分片 → 用上传人 SMB 会话 `open_write(append)` 追加到 `临时区/{batch_no}/{rel_path}`，同时把分片喂给 SHA-256 增量器（状态存内存，重启后丢失则在 complete 时重新流式读一遍算）。
5. `complete` 校验大小，写 `batch_files.fingerprint`；主图派发 `thumb`。
6. 全部 done → 批次「已暂存」。

### 11.2 核对 → 入库
前端只和 `batch_products` 打交道，直到终审通过，`ingest` 任务才把 `batch_products` 转成 `products`、`product_tags`、`product_relations`。

### 11.3 下载
`GET /files/{id}/download` → 用当前用户 SMB 会话 `open_read` → `StreamingResponse`，支持 `Range`，NAS 拒绝即 403。

### 12.2 安全要点

- 首次建立全新环境时生成 `data/secret.key`，用于加密 API Key 和系统账号密码。已有密文时必须使用原密钥。受管安装以 ACL 限制配置和密钥访问，保留服务身份运行所需权限。
- 登录 Cookie 开启 `HttpOnly` 和 `SameSite=Lax`。服务端校验 API 写请求的来源并拒绝跨站写入。内网 HTTP 传输边界见第 17 节。
- 正式资源以 ID 定位。实时 NAS 浏览和存储设置使用受约束的共享内相对路径，服务端检查路径及区域，再按当前 SMB 会话的权限执行。
- 发送到百炼的内容按用途取最小范围，包括去除 EXIF 的送审图、查询或商品文本及仅用于候选排序的临时编号。搜索传输前脱敏，路径、账号、项目编号及企业名保留在内网。
- `oplog` 由应用追加，SQLite 触发器拒绝更新和删除。

## 13. 备份

- 调度默认在北京时间 03:00 使用 `VACUUM INTO` 生成一致的 SQLite 快照。归档含快照、加密配置、密钥、各文件 SHA-256 与资产身份清单。继续使用备份格式 1，可记录生成备份的应用版本。向量随库备份，缩略图缓存可从已授权的原图重新生成。
- 生产备份要求存在已发布资产，并且正式档案扫描核验一致。仅当尚无核验标记时，才检查本机保留的最近最多 7 份有校验回执的 ZIP 是否存在兼容备份。扫描发现差异或处于 `recovery.read_only` 时，定时和手动写入均停止。启用 `backup_on_publication` 后，正式发布可触发延迟备份，同一等待窗口内的发布合并处理。
- 系统账号先把归档写入 `/_工作台备份/` 的暂存文件，读回核对 SHA-256，再改为正式文件名。已存在的同名归档须匹配登记校验值。本机以 7 份已验证备份为保留目标，较早副本在再次核对 NAS 对应归档后删除。NAS 历史备份由运维保留。
- 管理页「资产恢复与索引管理」可列出 NAS 备份候选。检测只校验候选 ZIP 结构和清单格式。选定备份后，暂存任务核对逐文件 SHA-256、SQLite 完整性及外键、资产身份清单和密钥。在独立目录迁移数据库、撤销旧登录会话，并生成适配目标环境的只读配置和恢复报告。目标环境的 NAS 区域路径须与备份匹配。暂存任务还比对 NAS，报告备份后的已发布变更。
- 管理页暂存供核验。整库切换由运维在停机窗口执行，停止两边服务的写入，保留原库完整目录、配置和密钥，切换到验证过的目标库。使用原版本兼容的数据库、配置和密钥做回滚。核验实际权限、原链接和检索后，确认正式 NAS 只留一套写入实例，再启用业务写入。具体操作见 [Windows 部署和运维](../deploy/README.md#数据恢复)。

## 14. 巡检与档案

### 14.1 档案写入器
- 写文件采用「写临时名 → 校验 → rename」，避免半截文件。
- TXT 项目档案以「结束标记：完」结束，商品 JSON 用有效的 `结束标记` 字段。首次入库的档案来自已确认批次。后续档案以正式卡片柜为准。巡检比对两边并登记待修复差异。
- 档案记录项目、商品、文件和历史版本的稳定身份、完整文件指纹、确认标签、关系及永久链接。发布凭据将正式项目与当时的路径、资产版本和档案摘要绑定。

### 14.2 巡检
- 系统账号只读会话，02:00 运行。
- 遍历 `/设计资产/`：按项目文件夹名解析编号 → 与 `projects` 对照 → 更新 `current_path`。
- 每项目 `list` 文件（名、大小、mtime）与 `files` 比对；变化的再算**完整 SHA-256**。仅在能通过稳定身份／指纹唯一定位时自动改物理路径并记录违规，不自动改公司、行业、中标业务字段。内容被覆盖时保留原指纹，标记漂移、允许警示性访问，待双审后才正式接受。
- 结果写 `inspection_findings`，摘要进管理员待办。
- 巡检通过系统账号只读访问 NAS。档案修复创建双审批次，审批通过后由本轮终审会话写回档案。

### 14.3 启动检测与档案恢复

- 本地库不可读、迁移失败，或已有密文缺少可用密钥时，`/api/health` 和业务 API 通过 503 提示离线恢复或核对密钥。可启动时先提供 SQLite 状态。生产服务后台用系统账号抽查正式路径和短凭据，最多检查 36 项，遍历预算 6 秒，NAS 连接超时设置上限为 3 秒。发现抽查凭据在本地缺失或版本偏旧时提示扫描。本地空库在未查清时提示待确认。实时 NAS 浏览直接按本人权限读取共享，已入库视图和两种检索依赖本地正式目录记录。
- 管理员可按需运行完整扫描，逐项目核对已发布的 NAS 档案、凭据、身份与完整 SHA-256，输出补录、更新、冲突、仅本地、待确认和不可读取的结果。确认计划后，恢复任务再次验证凭据和文件指纹，按项目原子登记可恢复项并重建正式向量。待审批次占用、身份冲突、缺少证据或权限不足的项目留在报告中处理。应用恢复计划后须重新扫描，扫描一致才更新备份所需的核验标记。
- `recovery.read_only: true` 支持同一 NAS 的并行核验，将本实例的 NAS 文件操作限制为读取，并停用 NAS 备份。增量恢复仍可写入本地 SQLite。在新旧环境间交接写入前，先核对报告和现场权限。只有档案仍可读取并有发布证据时，才能通过档案恢复该项目。数据库和全部备份丢失时，审核、角色和操作日志只能按仍存的数据说明。
- 需要人工确认的旧档案可以在离线工具中按报告提供档案路径、摘要和独立的发布依据。整库无备份重建使用 `scripts/rebuild_catalog.py` 在独立目录执行，流程见 [Windows 部署和运维](../deploy/README.md#数据恢复)。

## 16. 部署（Windows）

1. 目标主机准备系统级 Python 3.12、NTFS 数据盘、核验过的 Windows 安装包及 NSSM。公司 IT 配置固定内网域名、授权的 IPv4 网段和 TCP 8080 入站规则。工作台主机须能访问 NAS TCP 445。
2. 按部署手册运行 `deploy/install.ps1`，设置固定域名、NAS 主机、共享、工作根、系统账号与初始管理员。受管 NSSM 服务以 LocalService 运行，安装和恢复时都须核验配置、数据库与密钥的 ACL。
3. 在同一共享内为正式资产、上传临时区和备份区配置独立路径，按第 3.3 节设置账号权限。正式根中的业务目录由终审流程按需建立。
4. 迁移已有资产时先使用 `recovery.read_only: true` 核验目录数据、原链接和权限。通过管理页暂存备份或生成档案差异计划，也可使用 `scripts/restore_backup.py` 和 `scripts/rebuild_catalog.py`。升级、恢复、启用写入和回滚均按 [Windows 部署和运维](../deploy/README.md) 执行。
