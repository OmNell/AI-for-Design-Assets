- # NAS 设计资产工作台 · 开发约定

  ## 项目是什么
  公司内网的设计资产管理工作台：业务人员用浏览器把整理好的项目文件夹上传到群晖 NAS，
  AI 给商品主图打标签，经上传人核对、初审、终审后移入正式目录，之后可以搜索和下载。
  业务规则和当前实现说明见下列设计文档。历史差异和现场验收项见 docs/QUESTIONS.md。

  ## 文档优先级与当前基线
  1. docs/02-入库流程.md —— 业务规则与50项已确认决策，以 v4.0 为准。
  2. docs/01-命名规范.md —— 目录层级、命名、历史H编号与预检规则。
  3. docs/03-技术架构.md —— 技术架构、数据状态、API、权限及持久化设计，以 v2.0 为准。
  4. docs/05-数据存储与向量关系.md —— NAS档案、SQLite、向量与版本一致性的补充细则。
  5. docs/04-检索方案.md —— V1 商品双路检索、项目检索与检索边界，以 v2.0 为准。
  6. docs/06-Codex分阶段提示词.md —— WP00～WP14 分阶段开发指导，以当前设计为约束。
  不得沿用旧版固定词表、一图拆多个商品卡片、型号去重合并、200MB以上快速指纹、
  普通账号自审、向量生成在已入库之后、或无冷静期提前删除的旧规则。
  现有代码实现与设计有差异时，先在 docs/QUESTIONS.md 记录，不自行宣称已经实现。

  ## 工作方式
  - 每次会话只做一个工作包（WP）。只做该包「要做」里的事，「不要做」里的事一律不碰。
  - 开始前先读 docs/PROGRESS.md 与 docs/QUESTIONS.md，了解已有代码及待适配差异，再读提示词指定的文档章节。
  - 不擅自修改 docs/ 下的设计文档。发现文档有疑问或缺口：写进 docs/QUESTIONS.md，
    遵循现有已确认规则与保守技术实现，不要自行发明业务规则。
  - 完成后：跑通全部自动化测试和前端构建；更新 docs/PROGRESS.md（本包完成了什么、
    有哪些已知限制、怎么手动验收）；提交 git，提交信息格式「WPxx: 一句话说明」。

  ## 技术栈（不要更换）
  后端：Python 3.12、FastAPI、Uvicorn、SQLAlchemy 2.x、Alembic、SQLite（WAL）、
        smbprotocol、httpx、Pillow、APScheduler、pydantic-settings、cryptography、pytest
  前端：React 18、TypeScript、Vite、Tailwind CSS 3.4、react-router、
        TanStack Query、zustand、react-hook-form、vitest
  不引入 Redis、Celery、Docker、其他数据库、其他 UI 组件库。需要新依赖时在 PROGRESS.md 里说明理由。

  ## 目录结构
  按 docs/03-技术架构.md 第 15 节。后端模块放 backend/app/services/<模块名>/，
  路由放 backend/app/api/，前端页面放 frontend/src/pages/。

  ## 运行模式（config.yaml 的 mode 字段）
  - dev：登录用配置文件里的假账号。NAS 用本地文件夹模拟（LocalFs，按角色模拟读写权限），AI 用固定返回的假模型。默认自动化测试无需连接真实 NAS 或百炼。
  - prod：生产登录使用要求签名的 SMB2/3 会话，经 TCP 445 核验 NAS 账号和配置共享。模型调用使用真实百炼。
  - 需要真实 NAS 的测试标记 @pytest.mark.nas，需要真实百炼的标记 @pytest.mark.bailian，
    默认跳过，由人在公司内网手动运行。

  ## 硬性规则
  - NAS 文件操作必须通过 NasFs 接口。业务文件操作使用当前操作人本人的会话。系统账号用于正式库只读巡检及恢复核验、备份区的核验和备份，不代用户写业务文件。
  - 正式目录 /设计资产/ 只有终审的会话能写；管理员仅通过本人NAS身份清理终态临时批次，wb-system不得访问临时区。
  - NAS 密码不落盘、不进日志、不进数据库。唯一落盘的凭据是系统账号密码和百炼 API Key，必须加密。
  - 所有 NAS 路径由后端根据 ID 拼接，接口不接受前端传来的完整路径。
  - 业务操作日志 oplog 只追加：代码里不写 UPDATE/DELETE，并用数据库触发器禁止。
  - 发给外部模型的只有主图的缩小图（长边 1024、去 EXIF）和标签文字；
    不发 NAS 路径、账号、立项编号、企业名、资料夹里的任何文件。
  - 每个改变状态的接口都要写 oplog，并做角色检查。
  - 固定11个自由文本标签字段，仅允许管理员修改 hint 和显示顺序；每字段必须人工确认，允许确认无法确定的空值；所有新增/替换主图至少一次视觉AI成功才可审核。
  - 同一轮默认由三个不同账号完成提交、初审、终审。仅配置指定单账号且符合 docs/02-入库流程.md §2.2 的首次入库可自审。审核人员只可通过或驳回，提交时锁定版本，所有入库后操作和物理删除均实行两级审核。
  - 全量SHA-256；首次入库的全部必要向量成功才标记已入库；更新先准备影子向量及档案再原子生效；模型升级蓝绿索引。
  - 一项目最多一个在途操作批次；终审通过前允许发起人填写原因终止整个批次，临时文件留给管理员人工清理。
  - 永久链接由固定内网域名 public_base_url 生成；工作台继续HTTP/8080，仅授权局域网访问，需明确披露凭据和Cookie明文风险。
  - WP00～WP06 的历史差异记录按当时版本理解。当前实现以代码及版本验证为准，仍待核对的差异记录在 docs/QUESTIONS.md。

  ## 代码风格
  - 标识符用英文；界面文字、错误提示、日志内容、注释用中文。
  - 后端：类型标注齐全；接口的请求和响应用 Pydantic 模型；业务逻辑在 services，路由里不写业务。
  - 前端：函数组件 + hooks；接口调用统一放 src/api；不用 any。
  - 状态机的状态名、表名、字段名以 docs/03-技术架构.md 第 6 节为最终设计；已存在数据库和迁移若不匹配，必须另行设计迁移，不得在文档任务中改代码。
  - 每个服务模块要有单元测试；每个接口至少一条成功和一条失败的集成测试。

  ## 界面风格
  - V1.1 采用 Tailwind 企业界面，复用 `frontend/src/components/ui/` 的共享组件。
  - 页面使用浅灰底色、白色面板、蓝色主交互与语义状态色。工作台首页与资产浏览采用侧栏、工作区及详情面板。
  - 保持授权下载、破坏性操作确认、固定永久链接与角色守卫。组件使用清晰的焦点、明示状态与键盘可达交互。
  - 中文界面，桌面浏览器优先（Chrome / Edge），不做移动端适配。
  ## 设计基线更新与历史进度
  - 2026-11-17 起采用50项业务规则对齐的新版文档。docs/PROGRESS.md 既有WP00～WP06开发记录保留原样，不代表符合新设计。
  - 当前仓库已经存在 backend/、frontend/、scripts/；严禁按旧的空仓库提示词重新初始化或覆盖现有代码。后续从待完成的工作包接续，并优先形成实现差异清单。
