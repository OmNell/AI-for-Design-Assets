# NAS 设计资产工作台 · 入库流程详细设计（v4.0 · 50项规则统一修订版）

> 版本：v4.0 · 2026-11-17。保留原 v3.1 目录与业务骨架，统一 50 项确认规则。
> V1.1.8 文档同步。补充生产登录、正式发布和换机恢复的实际流程。
> 依据：两轮业务对齐会议结果（《第二轮业务确认结果与技术方案调整报告》）及其后的技术确认。
> 范围：从登录工作台到项目正式入库，以及入库后的补充、改名、修改标签、作废、移动、物理删除。
> 不含：查找与下载的详细方案、技术选型、AI 提示词细节。
> 相对 v2 的变更见第 17 节。
> 50 项已确认规则见附录 A；第 18 节仅保留需要线下提供的数据和现场验收，不再要求重复确认已决事项。

---

## 1. 原则

1. 工作台只做三件事：上传（入库）、查找、下载。上线后是设计资产进出 NAS 的唯一合规入口。
2. 入库顺序：**业务整理在前，AI 打标在中，上传人核对，初审、终审两级把关，终审通过才进正式目录。**
3. **身份和权限以 NAS 为准。** 工作台不另建账号，不设可写的服务账号。
4. **正式目录只有终审能写。** 任何落到正式目录的变动，都由终审点击后、以终审本人的 NAS 身份执行。
5. 工作台对项目包内部**放什么、怎么放不做干涉**。它只解析 `套装/` `单品/` 里的主图，并保证从主图能回溯到所属项目和项目下的各类资料夹。
6. 行业、企业分类由设计 BU 与产品 BU 线下商定，上传时不做检查和约束。
7. 不往设计文件里写任何内容。文件身份靠指纹，商品身份靠系统发放的商品编号。
8. 外部模型只收到主图的缩小图和必要的文字，不收到 NAS 路径、账号和资料夹里的任何文件。
9. 绕过工作台直接改动 NAS 属于违规。工作台只负责记录合规操作、发现不合规变动。

## 2. 账号、角色与权限

### 2.1 登录

- 用户在内网浏览器打开工作台，输入自己的 NAS 账号和密码。
- 生产工作台直接连接配置的 NAS TCP 445，建立要求签名的 SMB2/3 会话并验证共享可访问，随后检查工作台账号状态、加载本地角色并签发会话。拒绝来宾、匿名会话与 DFS 共享。
- 个人密码仅在本次 SMB 登录或重新登录时使用，不落盘、不进数据库、不写日志。内网 HTTP 传输密码和会话 Cookie 的风险见第 18 节。
- 会话有效期 8 小时（可配置）。已经建立且健康的 SMB 文件连接允许完成当前文件传输；连接中断后保存进度并等待重新登录，不能用过期上传令牌单独开启新上传操作。
- 同一账号可在多台电脑独立登录，每次登录持有各自的 SMB 连接，退出或断连只影响对应登录。操作日志记录客户端来源地址。
- 生产环境使用工作台已登记的完整登录名。与已登记账号冲突的大小写、域或 UPN 写法会被拒绝，避免将同一 NAS 主体拆成多个工作台角色记录。
- 第一版只部署在公司内网。

### 2.2 角色

工作台维护一张「NAS 账号 → 角色」表，由管理员填写。未登记的账号默认是上传人。

| 角色 | 人数 | 在工作台能做什么 |
|---|---|---|
| 上传人 | 所有能登录的 NAS 用户 | 上传、核对标签、提交、处理驳回、终审通过前终止自己的批次；对已入库项目发起补充、改名、修改标签、作废；查找、下载 |
| 初审 | 指定的若干人 | 上传人的全部能力，加上：初审 |
| 终审 | 指定的若干人 | 上传人的全部能力，加上：终审、审核阶段核定最终存放路径、通过后执行入库、发起移动、整项目作废、物理删除、执行档案修复 |
| 管理员 | 项目负责人 | 维护角色表、标签字段、企业→行业对照表；查看巡检报告、日志、临时区占用；清理临时区；重试失败批次；更换批次责任人；核验和暂存备份、发起资产恢复、管理索引与缩略图 |

规则：

- 一个人可以有多个角色。
- 上传人、发起人或提交人持有对应审核角色时，可以审核本人批次。首次入库和入库后操作均适用。
- **同一轮的初审和终审由不同账号完成。** 审核人员可在不同轮次交换角色。
- 不按行业或部门划分数据范围。
- 审核人不在时批次积压等待，不设代理。

### 2.3 NAS 权限矩阵

| 区域 | 上传人、初审 | 终审 | 系统账号 `wb-system` |
|---|---|---|---|
| 临时区 | 读、写（按本人授权范围） | 读、写 | 无 |
| 正式目录 `/设计资产/` | **只读** | 读、写、移动、改名、删除 | 读 |

- 保留系统账号 `wb-system`：正式目录只读，临时区无权，备份目录读写。用于巡检、备份和按正式档案恢复本地卡片柜。
- 管理员个人 NAS 账号对整个临时区（含他人批次）拥有读取与删除权限，但不因管理员身份获得正式目录写权限。

### 2.4 每个动作用谁的身份

| 动作 | 身份 |
|---|---|
| 上传、核对阶段追加主图、撤回批次 | 上传人本人 |
| 初审 | 不写 NAS |
| 终审通过后的移动、发商品编号、写档案 | 终审本人 |
| 入库后的改名、合并、作废、移动、物理删除 | 终审本人 |
| 档案修复 | 双审通过后，由本轮终审本人写入 |
| 清理临时区 | 管理员本人 |
| 巡检、正式档案扫描与恢复核验 | 系统账号，正式目录只读 |
| 备份检测、暂存和写入 | 系统账号，按备份目录权限 |
| 重建缺失缩略图 | 当前管理员本人，按主图读取权限 |
| 下载、预览 | 当前登录用户本人 |

## 3. 目录与命名（摘要）

完整规则见《设计资产目录与命名规范（草案 v0.2）》。

```
/设计资产/
├── 01已中标项目/
│   └── 01酒业/                                行业（系统按对照表建）
│       └── 07泸州老窖/                         企业（系统按对照表建）
│           └── P2026-0012_泸州老窖_中秋礼盒/    项目（业务人员建）
│               ├── 01定稿文件/
│               ├── 02设计方案/
│               ├── 03拍摄照片及视频/
│               ├── 04授权文件/
│               ├── 05 详情页/
│               ├── 套装/         全家福主图（打标）
│               ├── 单品/         所有单品主图（打标），含从套装拆出的和独立的
│               ├── 套装档案/     系统生成
│               ├── 单品档案/     系统生成
│               ├── _历史版本/    系统生成
│               └── _项目档案.txt  系统生成
├── 02未中标项目/                  结构同上
└── _已作废项目/                   整项目作废后移到这里
```

- 项目文件夹名：`立项编号_企业名_项目名`。
- 立项编号：**沿用公司立项时的唯一编号**。历史项目没有编号的，上传人选择项目**实际所属年份**，系统按该年份发放 `H` 前缀唯一流水编号（如 `H2023-0001`）。格式校验规则待公司编号样例确定后补充。
- 五个资料夹名称按业务现状**原样使用**，含 `05 详情页` 中的空格。业务要求缺资料时也保留空文件夹；预检仅提醒，终审正式入库前自动补齐缺失目录。
- **资料夹内部放什么、怎么命名，工作台不检查、不干涉。**
- `套装/` 只放全家福，`单品/` 平铺放全部单品主图。文件名由产品部门命名，对系统只是展示名，不承担任何结构含义。
- 业务人员上传的包里不得出现系统生成的四项。

## 4. 数据对象、编号与状态

### 4.1 对象

卡片柜是工作台电脑上的本地数据库。

| 对象 | 关键内容 |
|---|---|
| 项目 | 立项编号、企业、行业、是否中标、项目名、当前路径、状态、编号来源（公司编号 / 系统补发） |
| 批次 | 批次号、所属项目、类型、责任人、状态、临时区路径、审核轮次、初审人、终审人 |
| 文件 | 相对路径、大小、修改时间、指纹、是否有效 |
| 商品 | 商品编号、类型（套装 / 单品）、展示名、主图文件、状态、档案路径 |
| 套装-单品关系 | 套装商品编号、单品商品编号、来源（AI 推荐 / 人工）。多对多 |
| 标签值 | 商品、字段、值、来源（AI / 人工）、AI 原值 |
| 历史版本 | 旧指纹、原位置、现位置、发生批次、日期 |
| 永久链接 | 指向商品、文件或项目 |
| 标签字段 | 固定 11 字段；管理员仅可调整填写说明 `hint` 与顺序，不能增删、更名、禁用 |
| 企业→行业对照表 | 企业标准名、别名、行业、序号。只由管理员按线下结论录入 |
| 角色表 | NAS 账号、角色 |
| 日志 | 只追加 |

批次类型：首次入库、补充、改名、修改标签及套装关系、作废、恢复、移动、物理删除、档案修复。所有入库后变更均走两级审核。

### 4.2 商品编号

- 格式：`立项编号-三位流水`，如 `P2026-0012-001`。
- 终审通过、执行入库时发放。套装和单品共用一套流水。
- 发放顺序：单品（按文件名排序）→ 套装。
- 一经发放不变：改展示名、替换主图、移动项目、改套装关系都不换号。
- 补充包新增的商品接着原项目往后排。

### 4.3 套装与单品的关系

文件夹不表达从属关系，关系由系统建立、由人确认：

1. 第一遍 AI 打完全部单品，得到每个单品的名称和标签。
2. 第二遍解析每张全家福时，把该项目**全部单品的名称和标签**一起交给模型，让它判断全家福里出现了哪些单品，输出推荐清单。
3. 核对页上每张套装图有「包含的单品」区域，AI 推荐的已勾选，上传人可取消、可补勾。**每张套装图的关系必须经人确认，否则不能提交。**
4. 一个单品可以属于多个套装。
5. 全家福里有而 `单品/` 里没有单独主图的商品，不能被单独搜索，系统不处理。
6. 入库后修改关系走「修改标签」审批线。

### 4.4 指纹

- 按文件内容计算的哈希值，上传时边接收边计算。
- **所有文件无论大小都计算完整 SHA-256**，不使用快速指纹作为正式身份依据。
- 记录在卡片柜、项目档案、SKU 档案三处；不同路径的相同内容文件仍获得不同文件身份。

### 4.5 永久链接

| 链接 | 指向 | 说明 |
|---|---|---|
| 商品链接 | 商品编号 | 永远指向该商品当前有效的主图 |
| 文件链接 | 某个具体文件 | 包括历史版本 |
| 项目链接 | 立项编号 | 打开项目页，按五个资料夹列出文件 |

搜索结果给商品链接和项目链接。**从主图到设计文件的映射是项目级的**：搜到商品 → 所属项目 → 项目下各资料夹。商品与具体源文件的一一对应需要人工标注，第一版不做，作为后续可选功能。

链接必须使用固定内网域名 `public_base_url`，不能使用易变化的服务器 IP。链接打开时验证登录身份，用登录人的 NAS 读权限取文件，并记访问日志；作废但未物理删除的资产显示「已作废」，有读取权限的用户仍可查看／下载历史文件；物理删除后保留状态页。

### 4.6 批次状态

```text
上传中 ↔ 上传中断 → 已暂存 → AI处理中 → 待核对
                      ↘ AI处理失败 ─重试→ AI处理中
待核对 ─全部主图AI成功且11字段逐项确认／关系已确认→ 待初审
待初审 ─通过→ 待终审 ─通过→ 入库中（9步含必要向量门禁）→ 已入库
   ↘驳回→ 已驳回 ←驳回↙                              ↘失败→ 入库异常→终审恢复
              └─提交人修改／重新提交→ 待初审（轮次+1）
未终审通过 ─提交人填写原因主动终止→ 已终止（不可恢复，释放锁）
```

- 首次入库：相同立项编号同时只有一个进行中的批次；已正式入库编号只能转补充。入库后操作：同一项目同时仅一个未完成批次。`入库异常` 不释放锁。实现数据库事务和部分唯一索引。
- 主图 AI 失败即使手工填写也不得提交；必须每张新增／替换主图至少 AI 视觉成功一次。空标签可以在明确确认「无法确定」后保留。
- 审核角色与同轮账号要求见第 2.2 节。待审数据提交即冻结（含 SHA-256），驳回后提交人才能修改。审核人只可通过或驳回。
- 发起人终审通过前可以**终止整个批次**（填写原因），终止不可撤销、不可解锁重新编辑；此前审核记录保留；终止不自动删 NAS 临时文件。已入库和已终止均为终态；异常恢复不是终态。
- 只有所有正式商品必要向量成功，才能从 `入库中` 转为 `已入库`；向量失败且限次重试未成功进入 `入库异常`，保留 NAS、SQLite 和已成功向量。
- 仅有权限的提交人、初审、终审和管理员可通过工作台查看 `入库中／入库异常` 的相关进度；普通用户不可搜索、预览、下载。

### 4.7 商品状态

有效 ↔ 已作废 → 已删除。作废恢复不产生新商品 ID；物理删除不可恢复。替换批次在审核／异常处理期间，正常检索继续展示旧版本。

## 5. 全流程总览

```
业务人员在本机整理好项目文件夹（历史项目须提供实际所属年份）
        ↓
① 登录                     NAS 账号密码
        ↓
② 首页 → 上传新项目         勾选是否中标 → 拖入文件夹
        ↓
③ 浏览器端预检              只拦真正会导致系统无法处理的问题
        ↓
④ 上传到 NAS 临时区         分片、断点续传；传完由上传人确认
        ↓
⑤ AI 处理                  查对照表得位置；打单品 → 打套装并推荐包含关系
        ↓
⑥ 上传人核对并提交          所有字段可改；处理黄色项；确认套装包含关系
        ↓
⑦ 初审                     整包通过 / 整包驳回
        ↓
⑧ 终审                     审核同一锁定版本；仅核定最终归档路径，不修改待审商品、标签、文件或关系；整包通过 / 驳回
        ↓ 通过
⑨ 入库执行                  终审身份：移动 → 发商品编号 → 写档案 → 登记 → 生成链接
        ↓
⑩ 已入库                    可搜索、可下载
```

## 6. 首页与发起上传

### 6.1 首页

**上传人**：
1. 待办条：「2 个批次等你核对」「1 个批次被驳回」。
2. 我的批次：批次号、项目、类型、状态、最后更新时间。
3. 入口：「上传新项目」「对已入库项目操作」。

**初审**多「待初审」页。**终审**多「待终审」页，以及「入库未完成」「待修复档案」提示。**管理员**多：巡检报告、日志、角色表、标签字段、对照表、临时区占用。

### 6.2 发起上传

1. 点「上传新项目」，勾选「已中标 / 未中标」。
2. 拖入项目文件夹（或点「选择文件夹」）。
3. 系统从文件夹名第一段读出立项编号：
   - 编号已在库中 → 转补充流程（13.2）；
   - 编号不在库中 → 进入预检。
4. 历史项目没有公司编号的，上传人在文件夹名第一段填 `H`，系统在上传确认页为其发放 `H2025-0001` 这样的编号，并提示上传人把本机文件夹改名后重新拖入（或由系统在临时区落盘时直接使用新名）。

### 6.3 历史项目

与新项目完全相同：业务人员把旧项目拉到本机、整理成规范结构、走浏览器上传。旧库在迁移期间不删减，迁移完成后由业务部门决定去留。公共素材第一阶段不纳入。

### 6.4 限制

- 一次只能上传一个项目文件夹，拖入多个即拦截。
- 同一个人同时只进行一个上传，第二个排队。

## 7. 选择文件夹与预检

### 7.1 交互

```
拖入文件夹 / 选择文件夹
   ↓ 浏览器只读取清单：相对路径、大小、修改时间，不上传内容
预检结果页
   ├── 左：文件夹树，红（拦截）/ 黄（提醒）/ 灰（忽略）
   ├── 右：问题清单，写明哪个文件、什么问题
   └── 底：「有 N 个拦截项，请修改后重新拖入」或「开始上传」
   ↓ 无拦截项，每类提醒都勾了「我已知晓」
确认框：P2026-0012 · 泸州老窖 · 已中标
        目标 01已中标项目 / 01酒业 / 07泸州老窖 /（企业不在对照表时显示「位置待定」）
        86 个文件 · 3.2 GB · 预计 12 分钟
   ↓ 确认
开始上传
```

- 所有浏览器支持拖入，并提供「选择文件夹」按钮兜底。不做 zip 上传。
- 预检在浏览器端完成，只有「编号是否已存在」询问服务器。
- 在本机改完后需重新拖入整个文件夹。
- 「已知晓」勾选记入批次，两级审核都能看到。

### 7.2 预检规则

原则：**只拦截会让系统无法处理的问题**；业务整理得是否规范，交给人审。

| # | 检查项 | 处理 |
|---|---|---|
| 1 | 项目文件夹名不是 `编号_企业_项目名` 三段，或编号段为空 | 拦截 |
| 2 | 立项编号已在库中 | 转补充流程 |
| 3 | 任意层级含文件系统非法字符 `\ / : * ? " < > \|` | 拦截 |
| 4 | 路径总长超过 200 字符 | 拦截 |
| 5 | 出现系统保留的文件夹或文件（`套装档案` `单品档案` `_历史版本` `_项目档案.txt`） | 拦截 |
| 6 | `套装/` 或 `单品/` 里有非图片文件或子文件夹 | 拦截 |
| 7 | 首次入库 `套装/` 和 `单品/` 都没有有效主图 | **拦截**；仅已有项目的文档补充允许无商品主图 |
| 8 | 01～05 任一资料夹缺失 | **提醒不拦截**，终审正式入库时自动补齐空资料夹 |
| 9 | 项目名含中点、全角标点、空格等不建议字符 | 提醒 |
| 10 | 根目录散文件、规定之外的文件夹 | 不检查 |
| 11 | 主图分辨率、文件名写法、同名 | 不检查（等产品部门命名规则确定后再评估） |
| 12 | `Thumbs.db` `.DS_Store` `desktop.ini` `~$` 临时文件 | 忽略，不上传 |

## 8. 上传

### 8.1 过程

1. 服务端创建批次，记录文件清单。
2. 浏览器把文件切成 8MB 分片，3 个文件并行（可配置）。
3. 服务端用上传人的 NAS 身份把分片写到 `临时区/批次号/相对路径`，不在工作台电脑落第二份。
4. 顺序：主图 → 小文件 → 大源文件。
5. 每个文件传完：核对大小，得到指纹。
6. 主图传完时生成三张小图存在工作台电脑本地缓存：300px 缩略图、1600px 预览图、长边 1024px 且去掉拍摄信息的送审图。本地缓存不写回 NAS。

### 8.2 页面

总进度条、当前文件、已完成数 / 总数、预计剩余时间；每个文件一行。

### 8.3 中断与续传

批次变为「上传中断」，已传的保留。首页点「继续上传」→ 重新拖入同一文件夹 → 按相对路径、大小、修改时间比对：已传完跳过，半途的续传，有变化的重传，清单不一致时列出差异让上传人确认。

### 8.4 会话超时

工作台会话过期时，已建立且健康的 SMB 传输可完成；若 SMB 连接断开，暂停并保存偏移，用户重新登录后恢复。上传令牌不能绕过有效认证重新开始操作。

### 8.5 取消

上传中取消：标记批次终止并保留必要日志；临时文件不自动删除，由管理员在终态批次人工清理。

### 8.6 传完后的确认

批次进入「已暂存」，显示「N 个文件已到达临时区，指纹已计算」。**上传人点「确认，开始 AI 处理」才进入下一步。**

### 8.7 临时区清理

不自动清理。管理员在「临时区占用」里人工决定。

## 9. AI 处理

### 9.1 顺序

1. **存放位置**：从文件夹名第二段取企业名，查对照表。
   - 查到 → 得到行业，输出推荐路径。
   - 查不到 → 位置标为「待定」。不调用模型猜行业，不提醒上传人，不阻塞流程。由终审在通过前从现有目录树选择；目录树里没有这家企业，终审暂不通过，等管理员按线下结论录入对照表后再处理。
2. **第一遍：单品**。逐张打标。
3. **第二遍：套装**。逐张打标，同时输入该项目全部单品的名称和标签，让模型推荐「包含的单品」。
4. 完成后批次变为「待核对」，责任人待办 +1。

### 9.2 打标规则

- 平台：阿里云百炼。具体模型在技术细节阶段确定。
- 只发送主图的送审图。资料夹里的任何文件都不发送。
- 标签字段与填写规则见 9.5（业务已确认）。模型按每个字段的填写说明自由填写。
- 模型另生成一段自由描述供搜索兜底。
- 并行 3 路（可配置）。每张图失败自动重试 3 次。

### 9.3 自动标黄

| 情况 | 标在哪 |
|---|---|
| 模型填了「无法判断」 | 该字段 |
| 单品主图里识别出多个商品 | 该图 |
| 套装推荐的单品清单为空 | 套装那张图 |

### 9.4 失败处理

| 情况 | 处理 |
|---|---|
| 部分图片重试 3 次仍失败 | 可进入核对查看失败原因并重试，但**失败主图不得提交审核**；不允许手工补标绕过 AI 至少成功一次的要求 |
| 全部失败 | 停在「AI 处理失败」；上传人和管理员都可「重试整批」；管理员收异常 |
| 超过 30 分钟无进展（可配置） | 提醒管理员 |

AI 处理中可撤回批次。

### 9.5 标签字段

| 字段 | 填什么（给模型和人的填写说明） | 示例 |
|---|---|---|
| 品类 | 这是什么东西 | 保温杯、雨伞、茶具套装 |
| 材质 | 主要材料 | 陶瓷、304 不锈钢、胡桃木 |
| 主色 | 主要颜色 | 中国红、哑光黑 |
| 风格 | 设计风格 | 国潮、极简、复古 |
| 节日场景 | 适用的具体节日；不针对节日就写「通用」 | 春节、中秋、圣诞、万圣节 |
| 受众群体 | 给谁用、送给谁 | 企业客户、员工、长辈、儿童 |
| 使用场景 | 用途和使用的场合 | 商务社交、日常居家、户外出行 |
| 尺寸 | 大小的描述 | 掌心大小、约 20cm 高、桌面摆件尺寸 |
| 工艺 | 制作或装饰工艺 | 烫金、激光雕刻、釉下彩 |
| 物料名称 | 物料的称呼 | 双层玻璃杯、伸缩折叠伞 |
| 结构 | 组成部分和形态结构 | 杯身加杯盖、三折伞骨、抽屉式礼盒 |

规则：

- **全部字段由大模型预填，人工可以任意修改。** 没有固定的可选值，填写内容是自由文本。
- **不限数量**：一个字段可以写多个值，用顿号「、」分隔。
- 模型无依据时返回空值／无法确定状态，不编造；人工逐字段确认「无法确定」后正式值存空，`确认状态`与`未确认`必须区分。
- 没有强制填写具体值的字段，但 11 个字段**全部必须逐项人工确认**。
- 同一个意思的不同说法（「过年」与「春节」、「领导」与「企业客户」）不在入库时统一，交给检索时的大模型理解。
- 字段固定恰好 11 个，不允许增删、更名、禁用；管理员仅允许调整 `hint` 和字段展示顺序；更新 `hint` 不追溯历史商品，查询解释缓存按版本失效。

### 10.1 谁能核对

批次责任人（默认上传人）和管理员。换人由管理员改责任人。

### 10.2 页面


### 10.3 规则

- **11 个字段必须逐项人工确认**，每个字段可选择确认具体值或确认「无法确定」（最终空值）；未确认不得提交。
- 每个字段是自由文本输入框，可以写多个值（顿号分隔），不限数量。输入时提示库里已经用过的说法供参考，可以不选。
- 每个字段显示来源，人工改过的悬停可见「AI 原值 → 人工值」。
- **AI 自动标黄的项必须处理**：改掉，或点「确认 AI 值正确」。
- 红色的 AI 失败主图：必须单张重试至至少成功一次；不得纯人工绕过。
- **每张套装图的「包含的单品」必须点「确认关系」。**
- 自由描述可修改。
- 批量修改：多选图片，统一设置若干字段。
- 自动保存草稿。
- 上传人不能修改存放位置，有异议写在备注里。
- 提交前可填「给审核的备注」。
- 「提交审核」仅在每张主图 AI 至少成功一次、11 字段逐项确认（含明确空值）、套装关系逐个确认（含明确「无关联单品」）、关系复核完成且提交快照锁定后可点击。

### 10.4 追加与移除主图

- **追加**：在核对页单独上传图片到批次的 `套装/` 或 `单品/`。新追加的图单独跑 AI；追加单品后，已确认的套装关系不自动改变，但相关套装会重新标黄提示复核。
- **移除**：移到批次回收区，不入库。移除的单品自动从所有套装关系里去掉。

资料夹内的文件在核对阶段不能增减。

## 11. 初审与终审

### 11.1 两级的共同点

- 两级审核使用相同的检查清单，由不同账号把关。
- 队列按提交时间排列，显示项目、上传人、商品数、文件量、等待时长、轮次。
- 审核页布局同核对页，标签**只读**。右侧审核信息：

```
存放位置   01已中标项目 / 01酒业 / 07泸州老窖        [修改]（终审可改；初审只能看）
           或：位置待定——企业「XX」不在对照表中
预检提醒   缺少 04授权文件 · 上传人已知晓
核对记录   人工修改 6 处 · 确认 AI 值 3 处 · 明确确认空值 1 项 · 追加 1 张
套装关系   中秋礼盒A → 酒瓶、月饼盒、手提袋（AI 推荐 3，人工补 0）
上传人备注 "……"
资料夹     01定稿文件 12 个 · 02设计方案 5 个 · 03拍摄 0 个 · 04授权 0 个 · 05 详情页 3 个
审核清单   □ 存放位置正确   □ 项目命名与编号无误   □ 一图一品
           □ 套装与单品关系正确   □ 标签合理   □ 无不当内容

[通过]   [驳回]
```

- **审核清单必须全部勾选才能通过。**
- 可在图片上钉意见，随驳回一起发出；通过则作废。
- **驳回必须填总体意见，整包驳回，退回上传人。** 上传人修改后重新提交，从初审重新开始，轮次 +1。审核页可见历次意见。
- 待审核超过 3 个工作日（可配置），提醒管理员。
- 不能部分通过。

### 11.2 初审

- 持有初审角色的账号可领取，包括本人提交的批次。
- 不能修改存放位置（看到"位置待定"也照常审核标签和结构）。
- 通过 → 批次进入「待终审」。

### 11.3 终审

- 具备终审角色、且未担任本轮初审的账号可领取。
- 可以**建议修正并确认**存放位置：中标状态、行业、企业从现有目录树中选择，记录前后值。审核人员不得修改提交的业务内容；终审选择的最终目录属于审核阶段路径决定，不更改商品待审快照；如公司名称变化，执行器联动项目文件夹名公司段。
- 位置待定且目录树里没有该企业：不能通过，页面提示"等待管理员录入对照表"。管理员录入后终审再处理。
- 通过 → 立即以终审身份执行入库（第 12 节）。

## 12. 入库执行

以**当前轮终审本人 NAS 会话**顺序执行，每步设置持久检查点，不可跨系统裸提交；失败从未完成的步骤继续。所有商品向量可用才标记已入库。

| 步 | 动作 |
|---|---|
| 1 | 检查立项编号／同名文件夹冲突及本批次合法占用 |
| 2 | 按对照表创建中标／行业／企业目录；不覆盖其他项目 |
| 3 | 移动项目目录至正式位置、清除已核对排除项、以终审 NAS 身份补齐缺失的五个规定资料夹 |
| 4 | 发放商品编号：先单品后套装，原子记录 `batch_products.product_code`；历史 H 编号使用上传人选择的项目实际年份 |
| 5 | 将确认数据写入 `单品档案/{product_code}.json`、`套装档案/{product_code}.json`，记录稳定 ID、链接、确认标签、关联与 SHA-256 |
| 6 | 建 `_历史版本/` 和 `_项目档案.txt`，完整保存项目、文件、商品稳定标识／永久链接／版本／业务信息 |
| 7 | 事务写 SQLite 正式卡片柜，项目状态先为「入库中」，不得提前对普通用户可见 |
| 8 | 生成／校验永久链接及档案一致性；`public_base_url` 使用固定内网域名 |
| 9 | 生成并核验全部必要的正式模型文本向量，以本轮终审身份在 NAS 写入并读回核验 `_历史版本/_发布凭据.json`，再提交 SQLite 的「已入库」可见状态并通知。失败限次重试后进入「入库异常」。 |

**补充／修改**：先准备变更与必要向量，使用持久检查点推进 NAS 档案和凭据，SQLite 在发布核验通过后切换正式状态。失败时沿检查点核查并续跑，旧的已发布状态与未完成变更按第 13 节处理。仅补文档不触发向量。

**恢复与幂等**：已经移动到 NAS 的文件、已写档案、已发商品编号、已生成链接及已成功向量必须能够按持久检查点识别；重跑只补失败任务，不能重复发号。用户 NAS 会话不可用时暂停，不使用 `wb-system` 代写。

**灾难恢复**：三层档案保留项目、商品、文件、历史版本、标签、关系和原永久 `link_id`。备份不可用时，按第 14.3 节核验可证明已发布的版本并恢复原有标识。

## 13. 入库后的操作

### 13.1 总则

所有正式资产变更，包括补充、替换、项目或商品改名、标签／描述／关系调整、作废、恢复、移动、物理删除、档案修复，统一实行 **发起 → 初审 → 终审 → 终审本人 NAS 身份执行**。即便是轻操作也不得跳过两级审核。提交人可凭对应角色参与一级审核。同轮初审人与终审人不同，审核人只能通过或驳回。提交后数据锁定，驳回重新提交重新两审。

同一已入库项目同一时刻只能有**一个**未完成操作批次；包括等待审核、执行中及异常待恢复。终审通过之前发起人可以填写原因并终止整个批次，终止释放锁但不自动删除临时文件；终审通过后不得直接终止。

### 13.2 补充与替换

- 已有项目仅依立项编号进入补充流程；无需商品主图的纯资料补充允许。每个上传文件按项目内相对路径判定新增、相同路径且相同完整 SHA-256（重复）或冲突；同内容不同路径仍有独立文件身份。
- 替换商品主图时上传人必须能选择 `existing_product_id`，**不依赖文件名一致**。原商品编号和商品链接沿用；旧主图转 `_历史版本/`，旧文件链接仍指向历史文件，新主图作为新文件取得自己的稳定文件身份。
- 新增／替换主图均须视觉 AI 成功一次。替换主图将原 11 标签与新 AI 结果并排展示，上传人逐项确认沿用原值／采用新值／人工改写；11 项不得漏确认，允许已确认的空值。
- 主图替换时原套装关联以「待复核」状态展示，受影响关联由提交人逐条确认保留、调整或解除；新增单品涉及的套装也须明确复核。套装可以显式确认「无关联单品」。
- 本批次仅在新 NAS 内容、新 SQLite 数据、新档案和**所有必要正式向量**准备并验证成功后统一生效。任一步失败不会使原正式项目失效；历史版本／关系变更在最终生效时登记。文档补充无需向量。

### 13.3 改名与企业名称校正

- 项目改名更新项目目录名；若终审校正企业，同步更新文件夹第二段公司名及目标路径，更新 SQLite、档案、链接目标，不改永久 ID；重名或路径冲突时阻止覆盖。
- 商品展示名可改，主图文件名按审核结果改；**单品／套装档案 JSON 文件名始终仅为商品编号**，展示名变化不改档案文件名。名称改变后需要必要文本向量提前准备，成功后切换。

### 13.4 修改标签、自由描述与套装关系

- 修改现有商品采用草稿／版本隔离，记录旧值、新值、审核人；影响商品文本的变化预生成新向量，若输入文本哈希未变则跳过。
- 关系变化保留版本历史；不改变商品主图的标签文本时不重复生成向量。双审和统一生效不可跳过。

### 13.5 作废与恢复

- 套装作废**仅作废套装本身**，不得勾选级联作废关联单品；关联暂时不生效但历史保留。若需单品作废必须另起双审批次。
- 单品作废时对应套装关系置为暂时失效，保留历史与变更版本。恢复时，仅对仍有效的套装且在作废后未被正式修改的关系自动恢复，其他不自动恢复。
- 作废商品退出正常搜索，但其旧商品／文件永久链接保留并显示「已作废」；具有 NAS 读取权限的人可以下载／预览尚在的历史文件。已物理删除则只显示删除信息。
- 整项目作废移动至 `_已作废项目/`。恢复时默认原位置；若原位置冲突或分类层级变化，终审在两级审核内选择其他有效位置，校验不覆盖目录，同步更新 NAS、SQLite、档案；所有永久链接 ID 不变。

### 13.6 移动

- 终审核准后修改中标分类、行业／企业目录并同步 NAS 路径、SQLite、档案；项目编号、商品与文件 ID、永久链接不变，检查目标冲突。
- 绕过工作台直接移动属于违规：仅身份唯一可靠时巡检纠正物理路径并发出管理员通知，不自动更改业务分类。

### 13.7 物理删除

- 仅已作废的历史文件、商品或整项目可申请；从最近一次有效作废时间开始**严格等待满 30 天**，无任何提前删除例外。
- 须通过双审，同轮初审与终审账号不同。终审人以本人 NAS 身份执行。删除前列出全部文件、大小、历史版本及风险，输入编号二次确认；不允许直接点击绕过审批。
- 写入预期消失清单并存长期的原身份、指纹、原因、时间及操作日志；链接保留并显示已删除，物理文件不能继续下载。

### 13.8 终止、异常恢复及临时区清理

- 终审通过前提交人可填写原因、二次确认后**终止**整个批次；终止状态不可重新编辑或提交，历史申请和各轮审核记录保留、释放项目级锁。
- 终止不自动删除 `/工作台临时区/` 文件。管理员在清理页使用本人 NAS 身份，逐项确认后仅删除已终止、已入库等终态批次剩余临时文件和经证明无关联的孤儿文件；活动中或异常待恢复批次禁止清理。
- 执行中断时保留已成功文件、向量和持久检查点，终审重新认证后仅补未完成操作；不擅自授权他人接管。

### 14.2 巡检

- 每天凌晨一次，**只读不写 NAS**，用只读巡检账号。
- 只列目录，发现变化才算指纹。

| 情况 | 处理 |
|---|---|
| 整个项目文件夹被移动 | 按编号认出，更新卡片柜路径 |
| 单个文件位置变、内容没变 | 指纹确认后更新路径 |
| 同一位置内容变了 | 报告「未经工作台的修改」 |
| 卡片柜里没有的文件 | 报告「未经工作台的新增」，不收录 |
| 文件找不到且不在「预期消失」名单 | 报告「丢失」 |
| 档案缺失、损坏、不一致 | 列入「待修复档案」 |

- 对待修复档案发起两级审核，通过后由本轮终审以本人 NAS 会话修复。
- 报告发给管理员。
- 链接找不到文件时按「记录路径 → 编号定位项目 → 文件名 + 大小 + 修改时间 → 完整指纹」四层查找。

### 14.3 换机与故障恢复

GitHub 提供工作台源码。原环境的 SQLite、密钥和业务资产通过以下恢复流程接续。新环境配置 NAS 并启动后，以管理员身份打开「资产恢复与索引管理」，先检测本地资产和 NAS 备份。

1. **核验现有备份。** 优先选择最近一份有效备份。网页可将备份解包至隔离目录，核对校验值、原密钥、SQLite 完整性和迁移结果。正式接管按部署手册停机切换，核验角色、原链接、检索和读写权限，再由新实例接手正式写入。
2. **扫描备份之外的正式档案。** 备份较旧时，在隔离恢复库扫描补齐已发布的版本。备份不可用时，也可用同一流程重建。系统账号只读扫描正式档案，管理员查看并确认计划后，后台按项目核验发布凭据、档案、文件完整 SHA-256 和正式向量，再更新本地卡片柜。
3. **保留原资产身份。** 恢复原项目、商品和文件身份，以及有证据的历史版本、人工确认标签、套装关系与 `link_id`。缺少凭据或版本冲突时保留证据，交由人工核验。完整审核、权限和操作日志依靠数据库备份或独立记录。

恢复后重新扫描，确认本地已发布资产与 NAS 一致，以满足生产备份的核验条件。文件访问继续按当前用户的 NAS 权限核验。暂存、差异检查和回滚步骤见[部署手册的数据恢复章节](../deploy/README.md#数据恢复)。

## 18. 现场落实与必要输入

- 如技术验证失败，记录事实、影响、临时限制和后续解决方案；不得自行更改用户已确认的业务规则。
